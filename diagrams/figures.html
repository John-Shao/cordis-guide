图 2-2 · 三种形态

插件可以是函数、对象，或 Service 子类

Loader 把它们统一解析成一个可调用体；差别只在是否需要公开服务。
// 1. 函数插件（最常用） export const name = 'hello' export function apply(ctx) { /* 注册 */ }
解析：函数本身即 apply。name 只用于诊断。
不需要 apply 方法
// 2. 对象插件 export const objectPlugin = { name: 'object-plugin', apply(ctx) { /* 注册 */ }, }
解析：plugin.apply。对象形态必须有可调用的 apply。
适合带元数据的工厂
// 3. 类插件（Service 子类） export class Greeter extends Service { constructor(ctx) { super(ctx, 'greeter') } }
解析：new 出实例即注册服务。子类本身就是插件。
要公开服务时才用
非法形态：既不是函数、也没有可调用 apply 的对象，会得到 invalid plugin, expect function or object with an "apply" method。
元数据字段：name · inject · Config（Standard Schema）· provide · intercept，三种形态通用。

图 3-1 · 状态机

Fiber 的六个状态

逻辑顺序与源码里的数值顺序不同：DISPOSED 的编号（4）比 UNLOADING（5）小。
PENDING 0
已声明，但 inject 的服务还没出现。
LOADING 1
apply 正在运行。
ACTIVE 2
apply 已完成，注册生效。
UNLOADING 5
disposer 正在运行。
DISPOSED 4
全部拆完，从注册表移除。
FAILED 3
apply 或配置校验抛错。
服务恢复后重新加载
FAILED 不是跳过
教程启动器会打印错误并以状态码 1 退出；配置校验失败同样落到这里。
PENDING 会静默
等待中的 fiber 不保持事件循环活跃；没有别的运行项时进程以 0 退出，不留一行日志。

Cordis 教程 · 第 4 章
图 4-2 · 依赖是连续的

inject 不是只检查一次

服务消失 → 依赖它的插件一起卸载；服务回来 → 它们再加载。这是热替换能安全换提供方的原因。
[t=150] 挂载提供方
consumer 进入 ACTIVE
[t=400] dispose 提供方
consumer 卸载并回卷 effect
实测（exp-reactive.ts） consumer ACTIVE, value = dyn ← 提供方出现后才启动 [t=400] dispose provider consumer effect reversed (unloaded) [t=650] mount provider again provider ACTIVE consumer ACTIVE, value = dyn ← 自动重新加载
机制
provide 的 disposer 调用 reflect.notify([name])；它扫描所有 inject 含该名字的 fiber，用依赖提供方的 fiber.uid 拼出 epoch：值变了就重启，缺了就卸载。
可替换性的来源
卸载 dsh-bash-local、挂上另一个 shell 提供方：所有注入 'shell' 的插件重启并用新实现，消费方一行代码都不用改。
代价：消费方必须假设自己会被重启，不能把状态留在模块顶层；跨重启的状态请交给服务实例或专门的持久化插件。

图 5-1 · 分发模式

五种分发，只有两种收集返回值

模式是事件公开约定的一部分；写插件前先确认它属于哪一种。
方法是否 await监听器顺序返回值短路条件（实测）
emit否注册顺序丢弃不会短路；返回的 promise 不被等待，异常只进 logger。
parallel是并发启动丢弃不会短路；全部结束才返回，任一失败都会汇成 AggregateError。
serial是逐个 await首个 bail 值isBailed：非 null、非 false、非 undefined 即胜出并停止后续。
bail否逐个同步调用首个 bail 值serial 的同步版；注意 0 和 '' 也算 bail 值。
waterfall—环绕中间件链条结果监听器不调用 next() 直接返回即否决下游。
实测（exp-dispatch.ts） s1 -> undefined s2 -> false s3 -> "hit" serial => hit ← s4 从未运行 p1 start (60ms) p2 start (10ms) p2 end p1 end parallel => settled ← 并发启动，一起等待
实测 bail b1 -> null b2 -> 0 bail => 0 ← 0 不是 null/false/undefined，算命中 源码 vendor/cordis/src/events.ts isBailed = v => v !== null && v !== false && v !== undefined

图 10-1 · 四问排查法

从“没反应”到定位，最多四步

每一问都有确定的检查动作和确定的输出。第 2、3 问覆盖绝大多数情况。
1
yml 被读到了吗
你在哪个目录跑的？ctx.baseUrl = process.cwd()。全静默通常是这里。
2
每个 name 能解析吗
跑 log-replay 看 buffer。Cannot find module = 拼写或 @cordisjs/*。
3
fiber 停在哪一态
跑 exp-states。state=0 且 inject 有 null = 缺提供方。
4
消息被吞了吗
buffer 有内容但终端空 = ConsoleExporter 挂载晚于消息。
命中后
修目录
改包名/路径
补提供方或 disabled 该行
调 yml 行序或延后报错时机
// 常见错误文本 → 直接指向修法 cannot get property "x" without inject → 加 inject cannot set property "x" without provide → 用 Service / ctx.provide INACTIVE_EFFECT cannot create effect on ... → 已 dispose 的上下文 invalid plugin, expect function or ... → 三种形态之一 ValidationError: invalid config: - $.x ... → 第 6 章
// harness 侧两条 TOOL_EXECUTOR_UNAVAILABLE → 组合里补 @deepseek-ai/dsh-tool-executor-native 整套静默 PENDING（无输出 · exit 0） → dsh-tools 缺 systemPrompt 提供方
别把“没打印”当“没发生”。加载期异常一律交给 ctx.logger.error（fiber.ts:686-691），进程以 0 退出；而 void (async () => ...) 里你自己发起的异常照常炸给 Node。前者靠 buffer，后者靠终端。
